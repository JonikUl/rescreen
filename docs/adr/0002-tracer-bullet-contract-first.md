# Tracer bullet и contract-first разработка

**Status:** accepted

Разработку v1 ведём не послойно (сначала весь конфиг, потом весь capture, ...), а двумя приёмами. Первый — tracer bullet: после каркаса проекта строим тонкий end-to-end срез (`rescreen run` одной Page сквозь все слои — конфиг, Capture с реальным Chromium, BaselineStorage, DiffEngine, примитивный Report, exit-коды) и останавливаемся на ручную проверку; только после неё наращиваем функциональность. Второй — contract-first: сначала фиксируем контракт модуля (TS-интерфейс с TSDoc: предусловия, постусловия, инварианты), затем пишем тесты, покрывающие контракт чёрным ящиком (happy path, пограничные случаи, инварианты, нарушения предусловий; подмена только на задокументированных швах вроде Capture), и только потом — реализацию.

Причины: самый рискованный шов — реальный рендеринг в Chromium (JS-слайдеры, стабилизация), и его нужно проверить до инвестиций в остальные слои; contract-first не даёт тестам прилипнуть к деталям реализации и делает швы явными, пока их дёшево менять.

## Consequences

- Нумерация тикетов в `.scratch/v1/issues/` отражает срез: 01 — каркас + сквозные контракты, 02 — tracer bullet со стоп-краном на ручную проверку, 03–09 — наращивание.
- Красные тесты без реализации в начале каждого тикета — норма, а не поломка.
- Промежуточный Report в срезе намеренно примитивен; его дизайн — отдельный тикет 07, не дорабатывать «заодно».
